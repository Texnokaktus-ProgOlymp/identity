# Журнал проблем и затруднений

## 2026-10-26 20:41 +03:00 — Restore MSBuild завершается без ошибок в диагностике

- **Задача / контекст:** Проверка переноса библиотеки в src и подключения интеграционных тестов NUnit/MTP.

- **Что произошло:** Обычный `dotnet restore` дважды завершился с кодом 1. При normal verbosity вывод содержал `Build FAILED`, но 0 ошибок и 0 предупреждений.

- **Предпринятые попытки:** Проверены SDK и global.json; повторён restore с подробностью normal, затем с `--disable-parallel -m:1`.

- **Решение:** `dotnet restore --ignore-failed-sources --disable-parallel -m:1` успешно восстановил оба проекта. Последующую сборку проверяем с `-m:1`.

- **Предполагаемая первопричина:** Возможно, ограничения среды мешают межпроцессной работе узлов MSBuild; точная причина не установлена.

- **Предлагаемое улучшение:** При такой конфигурации среды документировать последовательный режим MSBuild либо обеспечить диагностику и работу дочерних узлов.

## 2026-10-26 20:43 +03:00 — Песочница блокирует IPC Microsoft.Testing.Platform

- **Задача / контекст:** Запуск интеграционных тестов NUnit через нативный MTP runner в .NET 10.

- **Что произошло:** `dotnet test --no-build` завершился до обнаружения тестов с `UnauthorizedAccessException` в `NamedPipeClientStream.TryConnect` при подключении MTP к CLI.

- **Предпринятые попытки:** Тестовая сборка запущена напрямую через `dotnet <путь к сборке.dll>`; все 33 теста прошли. Затем повторён обычный `dotnet test --no-build` с разрешённой эскалацией.

- **Решение:** Вне песочницы стандартный запуск MTP через `dotnet test` также успешно выполнил все 33 теста.

- **Предполагаемая первопричина:** Ограничения доступа к named pipes в песочнице; сам runner и интеграционные тесты работают при доступном IPC.

- **Предлагаемое улучшение:** Обеспечить разрешённый локальный IPC для MTP либо документировать прямой запуск тестового executable как способ диагностики ограничений среды.

## 2026-10-27 13:25 +03:00 — Конфигурация фабрики применяется после чтения JWT-ключа

- **Задача / контекст:** Перевод интеграционных тестов библиотеки JWT на WebApplicationFactory с отдельным minimal API host-проектом.

- **Что произошло:** Настройка PublicKeyPath из ConfigureAppConfiguration фабрики не была доступна при вызове AddConfiguredJwtBearer в Program: библиотека читает конфигурацию и файл до WebApplication.Build().

- **Предпринятые попытки:** Проверен порядок вызовов в WebApplicationFactory и DeferredHostBuilder версии ASP.NET Core 10.0.14. Обычный callback конфигурации воспроизводится при сборке хоста, а ConfigureHostConfiguration передаётся entry point через аргументы запуска.

- **Решение:** В CustomWebApplicationFactory настройки передаются также через ConfigureHostConfiguration до вызова entry point. Тестовый host использует только переданные ему аргументы, чтобы ранняя регистрация не зависела от пользовательских appsettings и переменных окружения.

- **Предполагаемая первопричина:** Раннее чтение конфигурации в библиотеке предшествует этапу, на котором deferred host применяет стандартные callbacks фабрики.

- **Предлагаемое улучшение:** Сохранять явную раннюю передачу настроек при тестировании этой регистрации; при будущем изменении API рассмотреть стандартный Options lifecycle без потери понятной диагностики при запуске.

## 2026-10-27 13:33 +03:00 — Уточнение запуска WebApplicationFactory для библиотеки

- **Задача / контекст:** Удаление отдельного тестового host-проекта и перенос его pipeline в Startup внутри NUnit/MTP-сборки.

- **Что произошло:** Предыдущий вариант с minimal API потребовал отдельного entry point и ранней передачи настроек. Для библиотеки это оказалось лишним: WebApplicationFactory позволяет явно переопределить CreateHostBuilder и использовать Startup из той же тестовой сборки.

- **Предпринятые попытки:** Фабрика переведена на WebApplicationFactory<Startup> с Generic Host и UseStartup; проверены отдельный JWT-сценарий, полный набор из 34 тестов и отдельно два сценария пути по умолчанию.

- **Решение:** Тестовый Startup находится в Tools; явный CreateHostBuilder исключает использование точки входа NUnit/MTP в качестве приложения. Обычная host configuration применяется до Startup.ConfigureServices, поэтому обход с передачей настроек в аргументах больше не нужен. Это уточняет решение предыдущей записи от 2026-10-27.

- **Предполагаемая первопричина:** Первоначальная архитектура излишне опиралась на автоматическое обнаружение entry point; при явном построении Generic Host отдельный проект не требуется.

- **Предлагаемое улучшение:** Для подобных библиотек использовать Startup и явно создаваемый тестовый host в одном интеграционном проекте; сохранять отдельный host-проект только при самостоятельной необходимости.
